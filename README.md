# Job Application Agent

A two-part system that automates the tedious parts of applying to jobs: tailoring a CV to a specific job description with deterministic anti-fabrication guardrails, and driving the actual application (Workday and similar ATS platforms via a real browser protocol connection, plus email/form submission with mechanical validation) instead of hand-composing each one from scratch.

This is a **code skeleton**, not a runnable end-to-end product. All personal data (name, contact details, employer names, government IDs, compensation figures) has been stripped and replaced with environment-variable/config placeholders. It's here to show the actual architecture and the real bugs that got fixed while building it, not to be cloned and run as-is.

Built by directing an AI coding agent end-to-end rather than hand-writing every line. The architecture decisions, the guardrail rules, and the bug diagnoses below were mine; the agent wrote and iterated on the implementation under that direction.

## `cv_tailor_agent/` — CV tailoring pipeline

Takes a job description and a candidate's master resume data (`cv_master.yaml`, not included), and produces a tailored, scored CV.

The tailoring/critique step is **provider-agnostic by design**, not tied to one AI vendor:

- **`prompts.py`** builds a self-contained, ready-to-paste prompt (`prep-tailor-prompt` / `prep-critic-prompt` CLI commands) that can go into any chat AI — the "tailor" and "fresh-eyes critic" roles don't require a live API integration, since a human is already in the loop reviewing every application anyway. In practice, this is the path actually used: whichever AI is already driving the session plays both roles directly, no API key required.
- **`pipeline.py`** / **`llm.py`** additionally offer a fully-automated mode (`run-automated`) that drives the same tailor → guardrails → critic → score → freeze stages via a live Anthropic API call, for a deployment that wants zero-human-in-the-loop drafting. Both modes share the same `guardrails.py`/`scoring.py`/`contracts.py`, so a CV produced either way is checked identically.
- **`guardrails.py`** — deterministic checks that run before anything is considered acceptable: no invented facts or numbers not already in the master data, no fabricated claims, style rules (no em dashes, no "not X, it's Y" framing, no bare three-item lists).
- **`scoring.py`** — a composite score (structural quality + ATS keyword coverage + a critic's honesty pass). The one hard rule: **the critic can never inflate a score to clear a threshold**. If there's a genuine gap between the candidate's background and the job description, it shows up as a disclosed gap in the output, not a smoothed-over claim. A CV that scores below the threshold with a real, non-fabricable domain gap is frozen anyway (with an explicit `--accept-below-threshold` override flag) rather than argued up.
- **`registry.py`** / **`dashboard.py`** — a shared, file-based source of truth for every CV built and application sent, rendered as a static, filterable dashboard (search by field, paginated, no server required). Locked writes so a second concurrent process (e.g. another agent instance working a different job in parallel) can't silently corrupt it.
- **Batch commands (`validate-patch-batch`, `freeze-batch`)** — when several tailored CVs are being built in the same session, each one's own validate → critic-check → score → freeze chain is still sequential (that dependency is real: a critic review needs a validated patch, a freeze needs a passing critic), but *across* jobs there's no such dependency. These two commands take a JSON manifest of N jobs and run the batch in a single process invocation instead of N separate ones, regenerating the dashboard exactly once at the end. One failing item doesn't block the others.

## `job_application_agent/` — application submission & validation

Beyond CV tailoring, this half owns getting the tailored CV (and any accompanying free-text content — cover notes, form answers) actually submitted, with mechanical checks before anything goes out:

- **`patterns.py`** — classifies how a given job wants to be applied to (email, a named portal form, a Workday-style ATS) from the job posting's own text, rather than guessing.
- **`guardrails.py`** — the same style-rule checks as the CV pipeline (no em dash, no contrastive "not X, it's Y" framing, no bare three-item lists, no stacked crutch words), applied to free-text application content instead of fixed CV bullets.
- **`validation.py`** — a final mechanical gate before a human approves sending: does the drafted email's `To:`/`Subject:` match what the job posting actually specified, is a CV genuinely attached, is it the *exact* frozen file on record for this job (not a stale or wrong one), does the file actually exist on disk, does the signature's profile URL match the real one. Catches "wrong CV attached" and "subject doesn't match the JD" mechanically, before a human has to notice by eye.
- **`sourcing.py`** — a cheap, deliberately permissive triage filter for postings found while scanning, distinct from the deeper per-JD fit check: applying is cheap, so a false negative (skipping a job that was actually fine) is the costly error here, not a false positive.
- **`checklist.py`** / **`records_db.py`** — on-disk, per-application state (current form step, which upload slots have the real CV vs. a placeholder, submission status) and a durable record of exactly what content went out where. Conversational state doesn't survive a context-compaction event in an LLM agent session; a file does — this exists specifically because in-flight application state got lost across a session boundary once.
- **`workday_forms.py`** — the hardened Workday form-interaction helpers. The module docstring is effectively a bug log: every function encodes a real failure mode hit live and how it was fixed (see below).
- **`pwc_apply.py`** — end-to-end orchestration for one Workday tenant's application flow, built after a field-by-field approach (30-40+ separate script invocations per application) proved too slow and fragile to keep using.

### Real bugs this code fixes (not hypothetical)

- **Duplicate rows from click-retries**: a click that might have silently missed was retried, but a naive retry-without-checking sometimes fired twice, creating a genuine duplicate entry. Fixed with a settle-check after every retried click that trims the duplicate if one appears.
- **A stale bottom action bar eating clicks**: a fixed Save/Submit bar at the bottom of the viewport physically overlapped elements scrolled near the bottom, silently swallowing clicks that looked like they should have landed. Fixed by always scrolling an element to the center of the viewport before clicking it, not just checking it's "in view."
- **A race condition in a typeahead search**: a fixed timeout after pressing Enter moved on to the next search before results had actually rendered, causing a repeating loop of the same failed search. Fixed by polling for the actual results panel to appear instead of trusting a fixed delay.
- **A virtualized picker that ignores programmatic scrolling**: a two-level country/type picker rendered only ~4 DOM rows of a much longer list at a time, and setting `scrollTop` directly via JavaScript did nothing because the framework never saw a real scroll event. Fixed by firing an actual mouse-wheel event over the element instead.
- **A hidden ARIA-proxy date widget**: a date-of-birth field's real bounding box was a fraction of a pixel wide, causing every viewport-aware click to fail or silently miss. Fixed by focusing the underlying input directly via JavaScript rather than clicking it, then sending real per-character keystrokes instead of a single `.fill()` call (which looked correct in the DOM but never actually committed to the framework's internal state).
- **Typing a full email body into a rich-text compose window via simulated keystrokes**: a click-then-type sequence into a webmail client's contenteditable body raced against the editor's own initialization, silently dropping most of the typed text and leaving only a stray character — with no error surfaced, so it looked correct until an explicit text-content read-back caught the mismatch. Fixed by setting the body through the mail provider's own API/draft-creation call (atomic, no race possible) and reserving browser automation for the one thing with no non-browser path: attaching the file.
- **A "insert hyperlink" dialog that silently no-ops**: driving a rich-text editor's link-insertion dialog via automation intermittently created a link element with an empty/default href instead of the typed URL, with the dialog closing normally and no error. Rather than retry-looping an inherently flaky UI interaction, the fix was to avoid it: a bare URL in the body is auto-linkified by the mail client on its own, so the dialog step is unnecessary for the common case.

## What's deliberately not here

- `cv_master.yaml`, `applicant_profile.yaml`, the registry, any frozen output CVs, per-application checklists/records, and anything else under a `private/` directory in the original project — all real candidate data.
- Any hardcoded name, address, phone number, email, government ID, or compensation figure. Every place one of those was needed, the code now reads from an environment variable via a small `_profile()` / `CANDIDATE` lookup instead.
